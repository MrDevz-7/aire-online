# Conceptos de AirE_Online

Registro de los conceptos aprendidos en cada módulo del proyecto. Se completa al cerrar cada módulo, con un resumen corto de ideas (no de tareas).

## M1 — Monorepo y esqueleto del gateway

- **Git y monorepo:** git no guarda "renombres", guarda snapshots y los detecta por similitud de contenido; por eso mover archivos sin modificarlos (`git mv`, todos `R100`) conserva el historial. Un remote es solo una URL guardada, y renombrar el repo en GitHub redirige la URL vieja.
- **Gateway/BFF:** una puerta de entrada única entre el frontend y el engine, que queda interno; es el lugar donde después se agregan autenticación y límites sin repetirlos. CORS lo aplica el navegador, no el servidor: sirve para proteger a los usuarios, no es autenticación.
- **Middleware:** una cadena ordenada de funciones `(req, res, next)`; el orden define el comportamiento (helmet primero, el 404 después de las rutas, el manejador de errores al final, y `cors` responde el preflight antes de que llegue al logging).
- **`createApp` vs `listen` y configuración:** separar construir la app de abrir el puerto, e inyectar la config por parámetro, permite probar sin red. Las variables de entorno llegan como texto, así que se validan al arrancar (*fail fast*), con código de salida distinto de 0, y las del entorno real ganan sobre el `.env`.
- **Docker:** una imagen es la receta congelada y un contenedor es esa receta corriendo; el multi-stage deja el compilador fuera de la imagen final, el orden de las capas aprovecha la caché, y `CMD` en forma de lista hace que Node reciba `SIGTERM` y se apague ordenado.

## M1.1 — Higiene y seguridad

- **Rotar vs. revocar vs. borrar una clave filtrada:** borrarla del archivo actual no alcanza porque sigue viva en el historial de git; revocarla antes de tener el reemplazo funcionando corta el servicio. Rotar es el orden correcto: activar la clave nueva en todos lados, verificar que funciona, y recién ahí matar la vieja — nunca hay una ventana sin ninguna clave válida.
- **`git rm --cached` vs. borrar un archivo:** `--cached` saca el archivo del índice de git (deja de subirse) pero lo conserva en disco; sin `--cached`, git lo borra de los dos lados. Y estar en `.gitignore` no destrackea nada retroactivo: eso previene que un archivo *nuevo* se trackee, no afecta a uno que ya lo estaba.
- **Por qué no se reescribe el historial tras una fuga:** una clave revocada es un string inútil aunque siga visible en commits viejos — el riesgo real ya está neutralizado por la rotación, no por ocultarla. Reescribir historial (`filter-repo`/BFG) cambia el hash de todos los commits posteriores a la fuga, rompiendo cualquier referencia existente (tags, clones) para un beneficio que ya se consiguió gratis.
- **`.gitattributes`:** vive en el repo (a diferencia de `core.autocrlf`, que es config local de cada máquina) y fija una política de fin de línea explícita para cualquiera que clone, sin depender de la configuración personal de cada colaborador.
- **Auto-deploy:** republica el servicio solo con cada push a la rama configurada. Pausarlo no afecta lo que ya está corriendo; evita que pushes intermedios de un desarrollo en curso lleguen a producción antes de estar listos.
- **Cambiar una env var en un servicio ya corriendo no alcanza:** un proceso solo lee sus variables de entorno al arrancar: hace falta un restart o deploy para que una rotación de credenciales sea efectiva, aunque el panel ya muestre el valor nuevo guardado.

## M2 — Base de datos local, reciclaje y modelo de dominio

- **Contenedor efímero, volumen persistente:** el contenedor se puede borrar y recrear; los datos viven en un volumen fuera de él. Compose nombra el volumen `<proyecto>_<clave>`, y la imagen de Postgres solo crea usuario y base cuando el volumen está vacío, por eso un volumen nuevo se ve como una base nueva. Un tag de git (`pre-m2`) es la misma idea aplicada al código: un punto fijo desde el que recuperar lo retirado.
- **Prioridad de la configuración:** variable de entorno > `.env` > valor por defecto del código. Un `.env` viejo puede apuntar a una base equivocada (esta vez, una remota) sin ningún error; conviene verificar a qué host se conecta la app antes de correr una migración.
- **Migraciones:** un script versionado que lleva el esquema de un estado al siguiente y de vuelta. `autogenerate` solo redacta un borrador que se revisa; `alembic check` compara modelos contra base pero no ve los CHECK, así que también se inspecciona con `psql` y se prueba que la base rechace lo inválido.
- **`timestamptz` y datos derivados:** `timestamptz` guarda un instante absoluto (UTC) y evita la ambigüedad de zonas entre fuentes; las fechas de "día local" son `date`. Un dato derivado (el horizonte de un pronóstico) se calcula al consultar, porque guardarlo permitiría que las tres fechas se contradigan.
- **UNIQUE, CHECK e índice único parcial:** UNIQUE vale para toda la tabla, CHECK para una fila y un índice parcial solo para las filas que cumplen un WHERE (no hay dos alertas *abiertas* iguales, pero el historial puede repetirse). Los NULL cuentan como distintos salvo `NULLS NOT DISTINCT`, y hay reglas que la base no puede garantizar (fuentes distintas en un emparejamiento) y quedan en la lógica de la aplicación. Las enumeraciones van como VARCHAR + CHECK generado desde una tupla única, más fáciles de migrar que un ENUM nativo.

## M3 — Ingestión de OpenAQ y AQICN

- **Guard clause:** una verificación al principio que frena temprano y con un mensaje claro (la guarda de Alembic contra hosts no locales), en vez de dejar que un error de configuración se propague en silencio; la salida deliberada (`ALLOW_REMOTE_MIGRATION=1`) obliga a decidir en lugar de equivocarse. Los mensajes de error muestran el host, nunca la URL con la contraseña, y por lo mismo se silencia el log de `httpx` cuando el token viaja en la URL.
- **Rate limit y resiliencia:** un tope de requests por clave sobre un servicio gratuito y compartido; la app coopera espaciando las llamadas, leyendo los headers `x-ratelimit-*` y esperando ante un 429 en vez de reintentar de inmediato. Una ingestión resiliente separa los fallos de una estación (se anotan y se sigue) de los sistémicos (clave inválida, cupo agotado: se corta y se devuelve lo ya descargado).
- **Cliente vs. servicio de ingestión:** un cliente sabe hablar con una API y traducir su JSON a una forma intermedia común; el servicio sabe hablar con la base y no conoce ninguna API. Así cada pieza se prueba sola y una fuente nueva solo tiene que devolver el mismo formato.
- **Upsert, `ON CONFLICT` y append-only:** `ON CONFLICT` le dice a Postgres qué hacer cuando un INSERT choca con un UNIQUE, y lo resuelve de forma atómica. Las estaciones usan `DO UPDATE` (se mantienen al día), las lecturas usan `DO NOTHING` porque son un registro append-only: no se corrige historial, se evita duplicarlo, y repetir una ingestión es inofensivo (idempotencia).
- **Medir antes de decidir:** una caja envolvente no es un país (cae sobre países vecinos), una API de mapa puede devolver solo un subconjunto con una caja grande, `/latest` devuelve el último valor aunque tenga años, y un campo con aspecto de epoch (`time.v`) puede ser hora local. Cada una se descubrió corriendo contra la API real y no leyendo la doc, y los índices AQI de AQICN no son las concentraciones de OpenAQ: esa conversión es de M5.

## M4 — Fuentes regionales scraped (IBOCA, SIATA)

- **Servicio de "capas" genérico**: un solo endpoint que devuelve datos distintos según un `id_capa` en el payload, en vez de un endpoint por tipo de dato. Cómodo para el frontend (agregar una capa = agregar un checkbox), incómodo para consumirlo desde afuera: hay que descubrir qué IDs existen. El catálogo de capas de SIATA estaba escrito en el HTML del menú (`onclick="cargar_capa('C_...')"`), y buscarlo ahí evitó sniffear la red capa por capa.
- **Circuit breaker en una investigación**: un límite explícito de intentos antes de parar y reportar (en este caso: 10-15 capas). Sin un tope, investigar se vuelve un pozo sin fondo — se probó esto, después aquello, y tres horas después no sabés dónde estás. El límite transforma "no lo encontré todavía" en "no lo encontré, y sé exactamente qué probé". La instancia previa del módulo se saturó exactamente por no haber tenido este tope.
- **Contrato compartido — `Protocol` vs `ABC`**: `ABC` exige herencia explícita (nominal), `Protocol` solo exige tener los métodos correctos (estructural, "duck typing"). Se eligió `Protocol` para no tener que tocar las fuentes de M3 solo por declarar conformidad: ya cumplían el contrato (tener `descargar()` que devuelve `ResultadoDescarga` y `close()`), y `isinstance(ClienteOpenAQ(), FuenteRegional)` da `True` sin que M3 sepa que existe. Un `Protocol` **no debe declarar más que el contrato real**: al principio incluía `fuente` como atributo de clase, pero `ClienteOpenAQ` lo tiene como constante de módulo, no de clase → daba `False`. Se ajustó el contrato, no la implementación. Regla: si el contrato te obliga a tocar código que ya funcionaba, el contrato estaba mal.
- **Frescura ≠ forma del dato**: la ingestión de M3 ya valida la forma (¿es un float finito? ¿la fecha es parseable?). Pero IBOCA devolvía `o3 = 0.00 ppb` fechado en 2022 — bien formado, y sin embargo basura. Un `0.00` de hoy es "no hay ozono ahora"; un `0.00` de 2022 es "el sensor está muerto desde hace 4 años". Guardarlos como si fueran contemporáneos produce discrepancias falsas en M5a (comparar un dato muerto contra uno real). La validación de frescura vive en la capa que ingiere (por fuente, porque cada fuente tiene su propia noción de "fresco"), no en el motor de reconciliación.
- **Payload form-urlencoded vs JSON**: SIATA espera el `id_capa` como `application/x-www-form-urlencoded` (el formato clásico de un `<form>` HTML), no como JSON. La diferencia es una línea en httpx (`data=` en vez de `json=`), pero el síntoma es engañoso: HTTP 200, JSON válido de vuelta, solo que **sin el campo `feature_vector`**. Cuando una API responde 200 con datos incompletos, sospechar del `Content-Type` antes que de la URL o los headers.
- **Anidamiento del JSON**: DevTools colapsa los niveles por defecto y eso engaña. En SIATA, los atributos útiles (`Codigo`, `ICA_PM25_Valor`) están en `atributos.descripcion.*`, un nivel más abajo de donde uno los esperaría (`atributos.*`). Leer jerarquías de un screenshot de DevTools es trampa; imprimir las claves con `list(d.keys())` o `json.dumps(...)[:2500]` es la fuente de verdad.
- **Merge por clave, no por request**: en IBOCA, una sola llamada trae todos los contaminantes juntos. En SIATA, cada contaminante está en su propia capa y la misma estación física aparece en varias. La solución es agrupar por `Codigo`: la primera vez que aparece un código se crea la estación, las siguientes se le pegan las lecturas. Un solo diccionario, orden garantizado por iteración del diccionario de capas.

## M5a — Reconciliación entre fuentes

- **Haversine + prefiltro por caja**: la Tierra es una esfera, no un plano, así que la distancia real entre dos coordenadas necesita trigonometría (Haversine), no una resta simple. Esa trigonometría es cara, así que antes de calcularla se descartan con una caja rectangular (comparar rangos, gratis) los pares que obviamente están lejos. PostGIS resolvería esto mejor a gran escala, pero es una dependencia de más para las pocas estaciones que maneja este proyecto.
- **Interpolación en una tabla de breakpoints**: convertir una concentración a AQI no es una fórmula continua — es ubicar en qué tramo de una tabla (EPA) cae el valor, y repartir proporcionalmente dentro de ese tramo. Un valor que no entra en ningún tramo (negativo, o absurdamente alto) devuelve `None` en vez de un número inventado: un dato convertido sobre una entrada inválida es peor que no tener comparación.
- **Idempotencia**: un cálculo es idempotente cuando correrlo varias veces con los mismos datos da siempre el mismo resultado final, sin duplicar ni cambiar lo ya guardado. Se logra con `UNIQUE` + `INSERT ... ON CONFLICT DO UPDATE`: la base, no el código, es la que garantiza que no haya duplicados — incluso si dos corridas se solaparan en el tiempo.
- **Validación semántica vs. validación de formato**: la ingestión (M3) valida que un dato esté bien *formado* (tipo correcto, unidad reconocible) y lo guarda igual, porque es un registro histórico de qué dijo cada fuente. Reconciliar (M5a) necesita además preguntarse si ese dato *tiene sentido físico* (una concentración negativa no existe) antes de promediarlo — son dos preguntas distintas, en dos capas distintas, a propósito.
- **Hallazgo real de esta corrida**: el motor de reconciliación está validado y funciona correctamente (confirmado con un smoke test manual: conversión AQI exacta, emparejamiento geográfico exacto en casos de 0.00 km), pero en producción hoy no generó emparejamientos reales porque la ventana de actividad de OpenAQ (7 días, decisión de M3) dejó activa una sola estación en todo el país, lejos de cualquier estación de AQICN. Las estaciones que sí coinciden geográficamente con AQICN (Puente Aranda, Guaymaral, Fontibón, Suba, varias de Medellín) existen en ambas fuentes a 0.00 km de distancia — quedaron inactivas en OpenAQ por falta de reporte reciente, no por un problema de este módulo.

## M5b — Captura y auditoría del pronóstico de AQICN

- **Traductor vs. regla de negocio**: el cliente AQICN traduce el `forecast.daily` completo a dataclasses (`PronosticoNormalizado`), sin filtrar por fecha. Filtrar "los días pasados no son pronóstico" es una regla de negocio que vive en la capa de servicio (que sí conoce "hoy" en hora local Colombia), no en el cliente. Esta separación hace que un test unitario del parser sea trivial: le das un dict, te devuelve una lista; no tiene que saber qué día es.
- **Hora local vs. UTC**: un día calendario en Colombia (UTC-5, sin DST) empieza a las 05:00 UTC del mismo día. Promediar lecturas de un día local exige traducir `[00:00, 24:00) local` a un rango `[05:00, 05:00+24h) UTC`, half-open para no contar dos veces la lectura de las 00:00 del día siguiente. Sin esta traducción, el promedio mezcla horas de días distintos según la zona horaria del servidor.
- **Idempotencia por filtrado del origen**: hay dos formas de idempotencia. La de Bloque 2 (`ON CONFLICT DO UPDATE`) escribe la fila y la deja igual a como estaba. La del cálculo de auditoría es más fuerte: el `SELECT` inicial solo ve filas `estado='pendiente'`, y el cálculo las transiciona a `resuelta`/`sin_datos`. La segunda corrida no ve ninguna fila pendiente vencida, y por lo tanto no ejecuta ningún `UPDATE` — no es que sobrescriba con el mismo valor, es que no toca nada.
- **Diagnóstico por desglose**: un contador único (`pronosticos_descartados: 112`) es opaco — no dice *por qué*. Separar el total en un desglose (`pronosticos_descartados_por_fecha: 112`) deja ver de un vistazo si el motivo es esperado (AQICN no mandó días objetivos futuros en esta corrida) o anómalo (parser roto). El total se mantiene como suma; solo se agrega la lectura del *por qué*.
- **Fixture cuando el happy path no se puede probar con datos reales**: si el proveedor no manda los datos que la lógica consume (AQICN no publicó días futuros para las estaciones colombianas en la ventana de prueba), la validación se hace inyectando filas a mano en la base (2 lecturas fake, 1 pronóstico fake, 1 auditoría pendiente), corriendo el endpoint, verificando los números, y limpiando con `DELETE` por id. Es validación real de la lógica, pero **no** de la integración end-to-end con el proveedor: esa queda como pendiente explícito, no como "probado".

## M5b.1 — Verificación del `forecast` real de AQICN para Colombia

- **Agregado retrospectivo vs. predicción**: un "forecast" puede ser dos cosas mecánicamente distintas — una predicción de días futuros o un resumen de días ya observados — y ambas viajan bajo el mismo nombre en distintas APIs. La forma de distinguirlas es observar las fechas: si son siempre anteriores a la fecha de la corrida y rotan hacia adelante a medida que pasa el tiempo (dos días ayer, uno hoy, mismos días relativos), es agregado retrospectivo; si aparecen fechas posteriores a hoy, es predicción.
- **Verificación empírica contra evidencia externa**: la investigación externa del brief sostenía que AQICN tenía forecast futuro para Bogotá y Medellín específicamente. La observación directa (6 estaciones + 2 feeds de ciudad + JSON crudo) refuta esa hipótesis: el patrón es uniforme y retrospectivo. Confiar en una fuente secundaria sin verificarla contra la API real puede llevar a construir arquitectura sobre una premisa falsa.
- **Costo de la prueba vs. costo de la certeza**: dos intentos (12 requests aprox.) alcanzaron para descartar una hipótesis. El brief autorizaba hasta 10 intentos; parar en 2 fue una decisión, no una limitación — agregar más muestras con el mismo patrón no cambia la conclusión, solo la demora. Reconocer "ya tengo la respuesta" es tan importante como reconocer "necesito seguir probando".
- **Alcance de la verificación**: el hallazgo es específico para Colombia. Distinguir si AQICN no predice para ningún país hoy, o si es solo para Colombia, o si es una degradación temporal, requiere probar una estación fuera de Colombia — fuera del scope de este módulo, queda como decisión de arquitectura pendiente para el PM.

## M5c — Pronósticos reales con Open-Meteo

- **Celda de un modelo global vs. estación puntual**: Open-Meteo devuelve el centro de la celda de la grilla de CAMS Global (~45 km de resolución), no la coordenada pedida. Varias estaciones de una misma ciudad caen en la misma celda y comparten pronóstico: no es un error, es la resolución del modelo. Consecuencia práctica: un pronóstico no es "de la estación X" sino "de la celda que contiene a la estación X"; si dos estaciones están en la misma celda, el pronóstico es idéntico aunque el modelo lo devuelva dos veces.
- **Primera captura del día gana**: hay tres formas de idempotencia ya vistas en el proyecto (`ON CONFLICT DO UPDATE`, filtrado por estado, y `ON CONFLICT DO NOTHING`). Para pronósticos se eligió la tercera: si el mismo día se captura dos veces, la fila existente no se toca. Es un registro histórico inmutable: si Open-Meteo corrige el pronóstico unas horas después, no pisamos la versión original. Reconstruir "qué se sabía en el momento" exige guardar la primera versión, no la última.
- **Valor diario sin inventar datos**: la serie de Open-Meteo viene horaria; el esquema pide un valor diario. El promedio de 24 horas es la agregación simple, pero descartando el día si falta CUALQUIER hora (D61) — promediar 20 horas sesga el resultado de forma no controlada, dependiendo de qué horas falten. El resultado es un número defendible, no una aproximación.
- **"Pedir 7 días" ≠ "tener 7 días"**: `forecast_days=7` es lo que se pide; lo que se guarda es lo que tenga 24 h no nulas. La medición real (Bloque 1) dio 3 días útiles con los últimos 3 vacíos o casi vacíos. Documentar el horizonte real y no el pedido es lo que separa un sistema honesto de uno que promete más de lo que puede entregar (D33).
- **Misma escala antes de restar**: comparar un pronóstico en µg/m³ con una lectura real en AQI es restar metros contra grados Celsius. Se convierten ambos a la misma escala antes de calcular el error. En este caso se convierte el pronóstico (a AQI) porque la tabla EPA ya existe en M5a, mientras que la conversión inversa (AQI → µg/m³) es ambigua por los tramos. Y hay un tercer grupo de contaminantes (o3, no2, so2, co) que NO se auditan: pasar µg/m³ a ppb/ppm requiere peso molecular y condiciones de temperatura/presión, y no se inventa un número. Se capturan, pero se marcan como `no_auditable`, sin ambigüedad.

## M6 — Reportes en lenguaje natural con Gemini

- **El LLM narra, el código calcula.** Gemini recibe una ficha de datos ya construida (cifras, fuentes, fecha, cobertura, limitaciones, atribuciones) y la cuenta en español. Nunca calcula, nunca estima, nunca completa datos que no estén en la ficha. Si el dato no está, lo dice.
- **Validar la salida con código.** Todo número del texto de Gemini tiene que poder rastrearse a la ficha (mismo valor tras normalizar coma/punto y admitir redondeo). Si un número no matchea, o si aparece un término prohibido ("machine learning", "garantiza", "con certeza"), o si el texto supera el largo máximo, se descarta el texto y se usa la plantilla determinística. El motivo del descarte queda registrado en `reportes.motivo_fallback`.
- **La lectura nunca llama al modelo.** `GET /api/reportes/{tipo}` sirve lo ya persistido. La generación es explícita (`POST /internal/reportes/generar`) y solo se dispara cuando alguien la pide. Consecuencia: el frontend puede mostrar reportes aunque Gemini esté caído o la cuota esté agotada.
- **Fallback determinístico siempre disponible.** Si no hay clave, si se agotó el tope diario del proyecto, si Gemini falla o si el texto no pasa el validador, se usa una plantilla en código normal que dice exactamente lo mismo que la ficha, sin agregar ni omitir datos. El producto funciona, es honesto, y no depende de la disponibilidad de un servicio externo.
- **Caché por hash de la ficha.** Un reporte se identifica por `(tipo, alcance, fecha_referencia, sha256 de la ficha)`. Si la ficha no cambió, se reutiliza el reporte existente y no se vuelve a llamar a Gemini. Como el hash no incluye campos de tiempo de generación, dos corridas con los mismos datos producen la misma clave.
- **Muestra chica: sin cifra.** El promedio de error de la auditoría solo se publica si hay al menos `MIN_DIAS_AUDITADOS_PARA_PROMEDIO` días objetivo distintos con auditorías calculadas por (contaminante, horizonte). Se cuentan días, no filas: estaciones que comparten celda de la grilla comparten pronóstico y no son muestras independientes. Con menos días, la ficha dice "todavía no hay suficientes días auditados" y no se publica ninguna cifra de error.

## Uso de Gemini y privacidad

Gemini se usa en el nivel gratuito de Google AI Studio, sin tarjeta ni billing. La clave se crea en `https://aistudio.google.com/apikey` y vive solo en el `.env` local; nunca se commitea.

**Qué se envía a Gemini:** la ficha de datos, que contiene únicamente cifras agregadas públicas de calidad del aire (promedios por ciudad, conteos de auditorías, fechas, atribuciones de fuentes). No se envían datos personales, datos de usuarios, ni texto libre de terceros. Los nombres de estación que aparecen en la ficha vienen de fuentes públicas (IBOCA, SIATA, AQICN) y se tratan como datos, nunca como instrucciones.

**Condiciones del nivel gratuito:** Google puede usar el contenido enviado para mejorar sus productos. Es aceptable porque solo se envían cifras agregadas y públicas. Los límites por modelo del nivel gratuito ya no se publican; se ven por proyecto en la consola de AI Studio. Por eso el proyecto tiene un tope diario configurable (`GEMINI_MAX_LLAMADAS_DIA`, default 10) y fallback determinístico: si la cuota se agota, el producto sigue funcionando con plantilla.

**Modelo principal:** `gemini-3.8-flash`. Lista de reserva por `GEMINI_MODELOS_FALLBACK` (`gemini-3.5-flash-lite`, `gemini-3.1-flash-lite`), que se prueban en orden si el principal no está disponible.

**Resiliencia medida en la corrida real:** el 503 (`UNAVAILABLE`) de `gemini-3.8-flash` es recurrente. La estrategia que funciona es rotar keys del mismo modelo (hasta que una responda) y cascada de modelos si todas fallan. Con 6 keys configuradas, la corrida real gastó entre 2 y 6 requests por reporte antes de encontrar una combinación que respondiera.

**Tope por reporte:** `GEMINI_MAX_INTENTOS_POR_REPORTE` (default 40) acota las rotaciones y reintentos de un solo reporte. Es defensa contra un bucle accidental; el tope diario es la protección real de cuota.

## M7 — Contrato de lectura, Docker Compose y gateway

- **Contrato de API como promesa estable.** Un contrato HTTP no es lo mismo que el SQL que hay detrás: es la forma de la petición y la respuesta, expresada en esquemas explícitos (Pydantic en el engine, Zod en el gateway). Los endpoints de lectura viven separados de la lógica de escritura (`services/lectura.py` solo lee; `services/ingestion.py` y `services/reconciliacion.py` escriben). Beneficio: cada endpoint se puede cachear, proxiar, autenticar y documentar por separado sin tocar los otros.
- **Red de Compose: cada servicio se alcanza por su nombre.** Dentro de un contenedor, `localhost` es el propio contenedor, no el host. Compose crea un DNS interno donde el nombre del servicio (por ejemplo `postgres`, `engine`) resuelve a su IP privada. Por eso `DATABASE_URL=postgresql+psycopg2://...@postgres:5432/...` y `ENGINE_URL=http://engine:8000`, y por eso la guarda D23 de Alembic ya permitía `postgres` como host local.
- **`docker compose restart` no recrea: no recarga `env_file`.** Las variables de entorno de un contenedor se fijan al **crearlo**, no al reiniciarlo. Cambiar el `.env` y hacer `docker compose restart engine` mantiene el env viejo dentro del contenedor. Para que se relea hay que **recrear**: `docker compose up -d --force-recreate engine`. Se descubrió probando el interruptor D74, que devolvía `historico_restringido: false` incluso con `FUENTES_SIN_HISTORICO_PUBLICO=aqicn` en el `.env`.
- **Healthchecks encadenados.** `depends_on` solo ordena el arranque, no garantiza disponibilidad. `condition: service_healthy` sí: Compose espera a que el healthcheck del servicio dependido pase a `healthy` antes de arrancar el siguiente. Así se encadenan `postgres → engine → gateway` y ninguno intenta conectarse antes de que el anterior esté listo.
- **BFF con lista blanca, no comodín.** Un gateway `/api/*` que reenvía todo lo que empiece con `/api` es cómodo, pero expone sin querer endpoints futuros del engine. La lista blanca explícita (una ruta registrada por cada endpoint del contrato) obliga a decidir caso por caso qué es público (D44, D76).
- **Timeout, reintento acotado y sobre de error uniforme.** El BFF no debe confiar en que el servicio de atrás esté sano: corta por timeout para no colgarse, reintenta **una sola vez** y solo en fallos transitorios (conexión, 502/503/504), y traduce cada fallo a un código accionable (`ENGINE_TIMEOUT`, `ENGINE_UNAVAILABLE`, `ENGINE_ERROR`, `BAD_REQUEST`) para que el frontend pueda reaccionar sin parsear mensajes. Los timeouts y los 4xx **no** se reintentan: no se arreglan con un segundo intento.

## M8 — Autenticación (JWT), usuarios y rutas administrativas protegidas

- **Autenticación vs. autorización, y secreto entre servicios.** Autenticar es responder "¿quién sos?"; autorizar, "¿qué podés hacer?". El login con JWT es autenticación; el rol `admin` en el token es autorización. Entre dos procesos del mismo sistema, la forma más simple de que uno sepa que quien llama es el otro es un secreto compartido que viaja en una cabecera y se compara en tiempo constante: `hmac.compare_digest` sobre el SHA-256 de ambos lados (mismo largo siempre, no filtra por timing).
- **Hash lento con sal, y por qué el refresh token se guarda hasheado.** Las contraseñas se guardan como una huella *lenta* (scrypt) con sal aleatoria por usuario; el costo es la defensa. El refresh token ya es aleatorio de 32 bytes: no hay nada que adivinar, así que basta con un SHA-256 (irreversible, no brute-forceable) para que, si la tabla se filtra, los tokens no sirvan.
- **JWT de vida corta + refresh con rotación.** Un access token firmado (no cifrado: se lee, no se modifica) vive 15 minutos. El refresh vive 7 días, va en cookie `httpOnly` y rota en cada uso: el anterior queda revocado y apunta al nuevo. Si el token viejo vuelve a aparecer, es robo: el engine revoca **todas** las sesiones activas del usuario (señal de compromiso, no solo un rechazo).
- **Cookie `httpOnly` y CSRF por `Origin`.** La cookie de refresco no la lee JS (defensa contra XSS de lectura) y solo viaja a `/api/auth` (no en cada request). Como el navegador la adjunta automáticamente, `refresh` y `logout` exigen `Origin` explícito contra la lista de CORS: los navegadores lo mandan siempre; un sitio atacante manda el suyo y se rechaza.
- **Lista blanca explícita, no comodines.** El proxy administrativo no expone "todo lo que esté bajo `/internal/`": expone las 9 rutas de disparo, una por una, con Zod estricto por ruta. Lo que no está listado devuelve 404 sin importar qué exista del otro lado. Los endpoints de usuarios y sesiones (`/internal/usuarios*`, `/internal/sesiones*`) no aparecen: son de uso exclusivo de `/api/auth/*`.
